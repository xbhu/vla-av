# UC A3 Setup Notes: LoRA Fine-Tuning on AutoVLA for Memorization vs. Learning Test

## Architecture findings (relevant to why the fine-tuning approach was chosen this way)

- AutoVLA's action codebook is a **fixed, offline-clustered** vocabulary, not an
  end-to-end trained VQ-VAE. Generated by `tools/action_token/action_token_cluster.py`
  using a K-disk clustering algorithm (`Kdisk_cluster`, default `--num_cluster 2048`,
  sampling up to `--n_trajs 2048000` trajectory segments). The codebook is pickled and
  loaded read-only at training/inference time; it is never updated by gradient descent.
- Action tokens are **not** predicted by a separate action head. `ActionTokenizer`
  remaps the 2048 action tokens onto the base Qwen2.5-VL vocabulary's least-used token
  IDs (`action_start_id: 151665` for the 3B model), and both text and action tokens are
  predicted by the same shared LM head via standard next-token prediction
  (`models/autovla.py`, `shift_logits` / `vocab_size` computed once, no branching).
  Confirmed by `run_rft.py`'s LoRA wrapping target: `get_peft_model(model.autovla.vlm, ...)`
  applies to the whole VLM backbone, not a separate module.
- Codebook was generated from a much larger corpus (`n_trajs` default 2,048,000 segments),
  independent of the nuScenes-mini train split used for A3 fine-tuning. This means any
  memorization observed in A3 is attributable to the fine-tuning step itself, not to the
  codebook's own generation process.

## Fine-tuning setup: run_sft_a3.py (derived from official tools/run_sft.py)

Official `run_sft.py` performs full-parameter SFT on Qwen2.5-VL-3B via multi-node FSDP
(`FSDPStrategy`), with no LoRA support and no checkpoint-continuation path (the relevant
lines are present but commented out). Neither fits A3's constraints: single RTX A2000
12GB, and the experiment specifically calls for LoRA-only fine-tuning (not full-parameter)
to keep methodology consistent with LLM UC6 / VLM UC1's frozen-backbone + LoRA approach.

`tools/run_sft_a3.py` was generated from `tools/run_sft.py` via a scripted, string-match
patch (`a3_setup/usecaseA3_build_run_sft_a3.py`) rather than a manual edit, with each
replacement asserting an exact single match before writing, so a silent partial-patch
failure is impossible. Three changes:

1. Added `from peft import get_peft_model, LoraConfig, TaskType`.
2. After `model = SFTAutoVLA(config)` (gradient_checkpointing_enable() call preserved in
   place), inserted: load `AutoVLA_PDMS_89.ckpt` state_dict with `strict=False` (BEFORE
   LoRA wrapping, matching the proven working order in the official `run_rft.py`), print
   missing/unexpected key counts explicitly (asserts `missing_keys < 50` to fail fast
   rather than silently training on an unloaded base model -- same bug class as A2's
   original checkpoint key-prefix issue), then wrap `model.autovla.vlm` with LoRA
   (target_modules: q_proj/v_proj/k_proj/o_proj, r=8, alpha=8, dropout=0.1) if
   `config['model']['lora']['use']` is set, then cast the whole model to bfloat16.
3. Replaced `FSDPStrategy(...)` (multi-node, sharded, mixed-precision plugin) with
   `devices=1, strategy="auto", precision="bf16-true"` for single-GPU training.

Smoke test (`train_sample_size: 5`, `epochs: 1`) confirmed: `missing_keys=0,
unexpected_keys=0` on checkpoint load; LoRA trainable params = 3,686,400 / 3,761,948,672
(0.098%); no CUDA OOM; ~3 min total (5 train steps + full val pass).

## CoT (use_cot) decision: disabled

Official `config/training/qwen2.5-vl-3B-mix-sft.yaml` template has `use_cot: true`.
`tools/preprocessing/nusc_sample_generation.py` only populates real chain-of-thought
text (`cot_output` = [fov, perception, move_intent, prediction, planning_instruction])
for samples whose scene token is found in a supplied `--drivelm_path` DriveLM annotation
file. Without that argument, `cot_output = []` for every sample (confirmed by code read,
lines ~272-363).

A3's train-split preprocessing was run without `--drivelm_path` (matching A2's val-split
precedent, which also omitted it). To avoid training on empty CoT targets while a config
flag falsely claims CoT supervision is present, `use_cot` was set to `false` in the A3
yaml. Verified in `dataset_utils/sft_dataset.py`: the `if not self.using_cot:` branch
builds `assistant_content` purely from `gt_action_idx` and never references `gt_cot`, so
this is a clean, safe path -- not a workaround with side effects.

This also keeps the experiment's variables focused: A3 is about action-token
memorization, not CoT reasoning quality, so removing CoT avoids an uncontrolled second
learning objective.

## Bug found and fixed: built-in Lightning validation loop bypasses A2's degenerate-GT filter

A2 found that ~16% of val samples have GT future trajectories padded to a static
(non-moving) value due to insufficient future frames at scene boundaries, and fixed this
with a post-hoc filter living entirely inside the standalone eval script
(`tools/eval/nusc_eval_a2.py`) -- the filter was never applied to the underlying
preprocessed JSON files themselves.

`run_sft_a3.py`'s validation loop uses `SFTDataset` to read
`autovla_nusc_preprocessed_val` directly, with no equivalent filter. Smoke test confirmed
this: validation ran over all 150 raw samples, not the ~126 A2-filtered ones. Since A3's
core metric is the train/val loss gap (used to judge memorization vs. learning), an
unfiltered val set would contaminate that gap with degenerate-GT noise unrelated to
generalization.

Fix: `a3_setup/usecaseA3_filter_val_degenerate_gt.py` reuses A2's exact criterion
(`sum(future_mask[:6]) == 6` to keep, reusing the logic from
`usecaseA2_check_degenerate_gt.py`) to produce a filtered copy,
`autovla_nusc_preprocessed_val_filtered`. Result: 126 kept / 24 skipped out of 150 --
exactly matching A2's documented ~16% degenerate rate, confirming the filter criterion is
correct. A3 yaml's `data.val.json_dataset_path` points to this filtered directory.

## Preprocessing commands used (train split, new for A3; val split reused A2's existing output)

```bash
conda run -n autovla_nusc_preprocess python tools/preprocessing/nusc_sample_generation.py \
    --nuscenes_path /home/xzh5180/Research/vla-av/datasets/nuscenes_mini \
    --output_dir /home/xzh5180/Research/vla-av/datasets/autovla_nusc_preprocessed_train \
    --split train \
    --version v1.0-mini
```
Result: 164 samples processed, 78 skipped (out of 404 raw candidate samples). The skip
count is expected to already reflect the official train-split degenerate-GT filter
(per A2's note that this filter "only applies to train split, not val split" in the
official codebase) -- i.e. `autovla_nusc_preprocessed_train` should already be clean, in
contrast to val which needed A3's separate post-hoc filter above. This was to be verified
directly rather than assumed (see open item below).

Note: this 164 count is unrelated to and not expected to match the "218 train samples"
figure from A1 (OpenDriveVLA's own, separate BEVFormer-based preprocessing pipeline with
different filtering criteria, e.g. `queue_length=5` history-frame requirements). The two
numbers come from different codebases and are not comparable.
